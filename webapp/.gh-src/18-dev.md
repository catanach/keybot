**One doc bug Product's check missed:** `deploy.sh:69` still says "press reset twice quickly to enter safe mode." One-line fix, should ride along with whatever closes this out.

**On the remaining gap Product flagged:** their read is technically correct, and I'd go further — a remote/no-touch trigger for the failure case is not really buildable, not as a matter of effort but of physics. `HOST_WRITES` and the "Hand the drive back" button only work because they ask a board that is still running its webserver to write a file to itself on the next boot (`main.py`'s `api_device_host_writes` → `device.set_host_writes` → the board, then `boot.py` reads it back). Every path in the doc that doesn't require touching the board depends on the board being reachable over WiFi. If `code.py` is crash-looping or the server's down, there is no channel left — CircuitPython has no out-of-band radio, no watchdog-triggered safe mode, nothing we can reach from the webapp. The two remaining recovery paths (double unplug, BOOTSEL) are physical by necessity, not by an implementation gap. So "trigger safe mode remotely" isn't a follow-up issue, it's not a thing — worth saying plainly so it doesn't get scoped as if it were solvable with more code.

The banner is buildable and cheap: `/status` already gets polled (`DEPLOY_POLL_SECONDS` in `main.py`); a banner that shows the two physical steps in plain language when polling times out (`DEPLOY_RESTART_TIMEOUT_SECONDS = 60` already exists as the threshold) is maybe a half-day — new UI state plus copy, no new device-side logic. I'd scope the follow-up issue as exactly that, and title it so it doesn't imply remote recovery is on the table.
